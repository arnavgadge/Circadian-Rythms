# CircadianIQ — Final Master Specification

**Release:** `v1.0.0-research-demo`

**Phase 18 (freeze/reproducibility/documentation) status:** see `release/version_manifest.json` field `phase_18_release_status`, and the final verdict at the end of this document.

This is the authoritative, consolidated technical specification for
CircadianIQ as of this release. It does not introduce any new
architectural decision — every statement below is drawn from, and must
not contradict, the phase-by-phase documentation already in `docs/`.
Where this document and an earlier phase doc appear to disagree, the

## 1. Project objective

CircadianIQ estimates a person's circadian phase (dim-light melatonin
onset, DLMO) from everyday behavioral and environmental signals — sleep
timing, light exposure, screen use, meals, exercise — evaluates how
well their actual behavior aligns with that estimated phase, identifies
which behaviors most affect the misalignment, and offers graduated,
safety-bounded behavioral recommendations. It is a **research/demo
system validated entirely on synthetic data**, not a clinical or
diagnostic product. See `docs/research_methodology.md` §1-2 for the
full problem definition and system objective.

## 2. Scientific foundation

CircadianIQ **computationally estimates** circadian phase from
behavioral/environmental proxies; it does not measure laboratory DLMO
and must never be presented as a clinical measurement or diagnosis
(`README.md` "Scientific boundary", carried through every user-facing
surface — see `docs/scientific_assumptions.md` for which numerical
assumptions are literature-backed vs. project modeling assumptions vs.
engineering choices, and `docs/paper/limitations_draft.md` /
`docs/research_handoff.md` for the synthetic-data-only scope statement).

## 3. System architecture

```
SQL database (authoritative longitudinal state)
    <->
Python computational pipeline (Phases 2-14)
    <->
FastAPI application layer, /api/v1 (Phase 15)
    <->
React + TypeScript dashboard (Phase 16)
```

See `docs/architecture_diagrams.md` diagram 1 for the full Mermaid
system diagram, and `docs/architecture.md` for the original Phase-1
architecture notes this was built on.

## 4. Database architecture

SQL is **authoritative longitudinal state** — every historical
prediction, alignment score, contributor ranking, recommendation,
intervention outcome, and safety flag lives in SQL and is only ever
read from or atomically written to by Python, never bypassed or
recomputed silently in a way that diverges from what's stored. See:
- `docs/final_database_design.md` — the final, consolidated schema reference (ER structure, all tables, relationships, normalization, PK/FK, indexes, constraints, transaction boundaries, immutable-vs-mutable table classification).
- `docs/architecture_diagrams.md` diagram 2 — the ER diagram.
- `docs/dbms_demo_queries.sql` — 14 runnable, commented queries demonstrating real relational-system capability against the schema.

**Known limitation #1** (preserved from Phase 17, not resolved): no
DB-level uniqueness constraint enforces "at most one
`circadian_labels.is_latest = true` row per (participant_id,
target_date)" — the invariant holds only through application discipline
(`supersede_existing_label` + single-writer SQLite serialization), not
a partial unique index. See `docs/final_database_design.md` for the
recommended (not yet applied) fix.

## 5. Synthetic dataset

Generated by `app/synthetic/` (Phase 3), a stateful, personality- and
chronotype-differentiated population simulator with a seeded, fully
reproducible generation process. See `docs/synthetic_data_generation.md`
and `docs/scientific_assumptions.md` for which generation parameters
(chronotype distribution, personality proportions, behavioral ranges)
are project modeling assumptions vs. engineering choices — none are
claimed as epidemiologically validated.

## 6. Feature engineering

68 behavioral/environmental features per prediction, built from a
strict trailing 6-day window (never the target day or any future day —
proven adversarially in Phase 17 audit 3, no temporal leakage found).
Circular time features use sin/cos encoding via
`app.synthetic.time_utils`, the single canonical circular-time
implementation imported everywhere clock math happens (Phase 17 audit
6: no naive-subtraction bug found anywhere in the system after one real
fix — see §17 below). See `docs/feature_engineering.md` and
`docs/final_ml_methodology.md`.

## 7. ML model

XGBoost, two independent models predicting sin(DLMO) and cos(DLMO)
(circular regression), trained on a strict **participant-level**
held-out split (no participant appears in both train and test; Phase
17 audit 4 re-verified zero overlap, including per-GroupKFold-fold).

**Validated held-out synthetic test result (frozen, do not alter):**
**"93.73% of held-out synthetic test windows were within ±60 minutes"**
(MAE 24.47 min, RMSE 31.86 min, median absolute error 19.71 min, bias
-0.82 min, n=4800 windows / 200 held-out participants). 5-fold CV: MAE
25.22 ± 1.20 min, within ±60min 93.03% ± 0.74%. Baselines: participant-
mean 57.2 min MAE / 67.6% within ±60min; MSFsc-proxy 342.1 min MAE /
0.0% within ±60min. **This describes synthetic-benchmark performance
only — it is never a claim about real-human accuracy.** Full
methodology, hyperparameters, stratified results, feature importance,
and SHAP interpretation: `docs/final_ml_methodology.md`. Machine-
readable results: `release/results/*.csv`. Figures: `release/figures/*.png`.

## 8. State engine

A stateful circadian estimator (intrinsic / adapted / current DLMO,
bounded ±2h / ±3h respectively from baseline, with a 60-minute daily
continuity cap) independent of the ML model, fused with it downstream.
Verified over 30/90/180-day trajectories with no drift, no numerical
instability, correct directional response to disturbance and recovery
(Phase 17 audit 7). See `docs/state_engine.md`.

## 9. DLMO fusion

Confidence-tier-weighted fusion of the XGBoost and state-engine
estimates, with disagreement-based confidence penalties and a
continuity cap. All four availability combinations (both, XGB-only,
state-only, neither) behave correctly — a "neither available" case
never fabricates a value (Phase 17 audit 8). See `docs/dlmo_fusion.md`.
Note: the isolated "fused MAE 12.89 min" diagnostic figure quoted in
`docs/dlmo_fusion.md` and `docs/paper/results_draft.md` §5 is inflated
by construction (the synthetic state estimate replays the same
generative model as ground truth) and must never be cited as a
real-world fusion accuracy claim — see `docs/paper/limitations_draft.md`.

## 10. Alignment

60% phase + 40% behavioral (25/25/20/15/15 sleep-consistency/morning-
light/screen/meals/social-jetlag). All outputs bounded [0,100],
monotonic in phase deviation, correct across midnight (Phase 17 audit
9). See `docs/alignment_engine.md`.

## 11. Contributors

60% normalized phase effect + 40% alignment deficit, exactly 5 core
signals, today's anomaly kept structurally separate from the 6-day
historical ranking (Phase 17 audit 10). See `docs/contributor_ranking.md`.

## 12. Recommendations

Exactly one primary + at most two supporting nudges, graduated targets
(50% fraction toward ideal), circular-safe midnight handling, no
medical language in the catalogue (Phase 17 audit 11, audit 18). See
`docs/recommendation_engine.md`.

## 13. Intervention feedback

Missing observations excluded from compliance (never counted as
non-compliance); baseline/intervention periods correctly separated;
three measurement phases (1 observational / 2 matched-observational /
3 regression-controlled) consistently labeled end to end (Phase 17
audit 12). See `docs/intervention_effectiveness.md`.

## 14. Personalization

Literature -> personal_ranking -> personal_effect -> adaptive_policy,
independent per intervention type. **The single highest-priority Phase
17 finding: an explicit temporal-replay proof confirmed personalization
state for day N depends only on data strictly before day N — no future
compliance, outcome, or DLMO data leaks backward.** Bandit sampling
requires an explicit caller-supplied RNG (no unseeded global
randomness). See `docs/personalization_engine.md`.

**Known limitation #3** (preserved, not resolved):
`app.personalization.db_adapter.latest_recommendation_id_for_type` is
not `as_of_date`-scoped — a catalogue-versioning gap if the
recommendation catalogue is ever edited mid-study. **This is not a
participant-data leak**; all participant behavioral/outcome data reads
are correctly scoped.

## 15. Safety

Confidence gate (≥80 HIGH / ≥60 MODERATE / ≥40 LOW / else NO_PREDICTION,
also gated on <50% completeness) -> 4 pattern detectors (persistent
late/early phase, continuous DLMO drift, low alignment despite
compliance) -> severity (continuous_dlmo_drift is the sole HIGH-
severity type; the rest are MODERATE) -> suppression. Normal
midnight-crossing behavior does not false-trigger drift detection
(Phase 17 audit 16-17). See `docs/safety_and_confidence.md` and
`docs/architecture_diagrams.md` diagram 7.

## 16. API

FastAPI, versioned `/api/v1`, strict read/write separation (`GET
/status` never triggers inference; only `POST /inference` computes
anything), idempotent, no raw DB objects or stack traces ever surfaced
to a client (two real leaks found and fixed in Phase 17, see §17
below). See `docs/api_architecture.md`.

## 17. Frontend

React + TypeScript, consumes the API exclusively — no DLMO, alignment,
contributor, safety, or recommendation computation in the UI (verified
via a grep-based domain-computation guard test in Phase 17 audit 20).
See `docs/ui_architecture.md`.

## 18. Validation

Phase 17 ran 30 numbered adversarial audit categories as executable
tests (not read-throughs), found and fixed 6 real defects (a circular-
time bug in meal-timing scoring, two related exception-leak defects in
the inference API, two unguarded pipeline stages that could crash
instead of degrading gracefully, and an Alembic in-process logging
bug), and documented 3 non-critical limitations rather than hiding or
silently fixing them. Final verdict: **CONDITIONAL PASS**. Full report:
`docs/system_validation_and_audit.md`.

## 19. Reproducibility

`python -m app.scripts.reproduce_release` — one-command, seed-
deterministic reproduction against a disposable database (never the
real dev DB by default). `python -m app.scripts.seed_demo_scenarios` —
deterministic demo participants. Both tested and working at authoring
time. See `docs/reproducibility.md`, `release/reproducibility_manifest.json`.

## 20. Assumptions

Every meaningful numerical constant in the system — DLMO state rates,
DLMO bounds, fusion weights, alignment weights, safety thresholds,
personalization thresholds, synthetic-generation distributions, and
more — is inventoried and classified LITERATURE-BACKED / PROJECT
MODELING ASSUMPTION / ENGINEERING CHOICE, with file:line citations. No
constant is classified literature-backed without an actual in-code
citation. See `docs/scientific_assumptions.md`.

## 21. Limitations

**Three known, documented, non-critical limitations (unchanged from
Phase 17, not silently fixed during Phase 18 packaging):**
1. No DB-level uniqueness constraint on `circadian_labels.is_latest`.
2. Structured version-provenance columns are incomplete (only the XGBoost model version is a queryable column).
3. `latest_recommendation_id_for_type` is not `as_of_date`-scoped (catalogue-versioning gap, not a participant-data leak).

Plus: synthetic-data-only validation (no real-human DLMO ground truth
anywhere in this release); the `feature_manifest_version` naming
inconsistency between the trained model's own metadata ("phase4-v1")
and the current code constant ("1.0.0") — a label mismatch, not a
feature-set change; no significance testing anywhere in the codebase
(no p-values are computed or should be cited from this system); the
fusion-diagnostic MAE figure's circularity (§9 above); an unauthenticated
prototype API (documented in `docs/api_architecture.md` "Prototype
security limitations", unchanged this phase). Full list:
`docs/paper/limitations_draft.md`, `docs/research_handoff.md`.

## 22. Future work

External real-world validation cohort, measured-DLMO/melatonin anchor
data, recalibration of every project-modeling-assumption constant
against real data, closing the 3 documented limitations, extending
structured version provenance to every result table, ablation studies
on feature groups, and the future real-data transition path (never
implemented in this release — see `docs/research_handoff.md` "Future
real-data path" and `docs/paper/future_work_draft.md`).
