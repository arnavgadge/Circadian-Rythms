# Methodology (Draft)

It condenses `docs/research_methodology.md` (the full 23-section technical methodology, itself synthesized from the phase-by-phase design documents in `docs/`) into paper-section form. **Release version:** v1.0.0-research-demo. **Phase 17 audit status:** CONDITIONAL PASS.

> **Global disclaimer:** CircadianIQ computationally *estimates* circadian phase (DLMO) from behavioral and environmental proxies. It has **never** been validated against real human DLMO measurements. Every dataset, metric, and diagnostic result described below is computed on **synthetic data** generated by CircadianIQ's own generative model.

---

## 1. Circadian Modeling Concept

CircadianIQ represents circadian phase with three layered DLMO concepts: **intrinsic DLMO** (a fixed biological predisposition set once per participant), **adapted DLMO** (a slowly-changing behavioral equilibrium), and **current DLMO** (a fast, day-to-day dynamic estimate). This three-layer structure is shared, unmodified, between the synthetic data generator (which produces ground-truth training trajectories) and a separate mechanistic state engine (which independently estimates `current_DLMO` from behavioral history with no dependency on the trained ML model). All numeric parameters governing this model (adaptation rates, pull rates, bounds) are the project's own synthetic modeling framework, not a claimed validated model of human circadian physiology.

## 2. Synthetic Data Generation

Because no real paired behavioral/DLMO dataset is available, CircadianIQ generates a synthetic longitudinal dataset of 1,000 participants x 30 days (30,000 participant-day records; 24,000 six-day-window-to-next-day sliding windows). Generation proceeds in three stages: (1) one-time participant generation, assigning chronotype (Early 27% / Intermediate 59% / Late 14%), a chronotype-conditioned MEQ score, and stable personality/sensitivity traits; (2) daily behavior generation from personality baseline plus weekday/weekend effect plus stochastic noise plus occasional disruption events, generated deliberately independently of the evolving DLMO state to avoid a circular learning problem; and (3) sequential day-by-day application of the three-layer state model, driven by that independently-generated behavior. Each numeric constant is labeled either source-backed (cited to the project document's literature references) or synthetic (a project modeling choice). Generation is byte-for-byte reproducible given a fixed seed, participant count, and day count.

## 3. Feature Engineering

The feature engineering layer converts exactly six previous complete calendar days of behavior into a 68-feature vector predicting the next day's `current_DLMO`: 48 raw daily circular-time signals (4 clock-time signals x 6 days, sin/cos encoded), 2 MSFsc features, 2 MEQ-derived features, 10 flat window aggregates, and 6 recency-weighted aggregates. A three-tier missing-data fallback chain (window → personal history → population default) resolves every feature with attached provenance; on the synthetic dataset, every window achieves `completeness == 1.0` by construction (no missingness was injected). Leakage prevention is enforced structurally: the feature window for target day N is always days N-6..N-1, verified by automated sanity checks on every generated dataset. All clock-time-valued signals throughout the system use circular sin/cos encoding and circular shortest-arc differences, never linear hour subtraction, so that a boundary such as 23:50→00:10 is correctly computed as a 20-minute difference.

## 4. Model Architecture and Training

Circadian phase is predicted as a regression over a circular target, solved as two independent `xgboost.XGBRegressor` models — one for sin(DLMO), one for cos(DLMO) — trained on the identical 68-feature manifest, decoded back to a clock hour via atan2-based unit-circle normalization. Hyperparameters (`n_estimators=500`, `max_depth=6`, `learning_rate=0.05`, `subsample=0.8`, `colsample_bytree=0.8`, `objective=reg:squarederror`) are the project's documented engineering starting point; no hyperparameter search was performed. Two independent single-output models were chosen over native multi-output XGBoost to preserve per-target interpretability for feature-importance and SHAP analysis.

Evaluation strictly separates participants, never rows: a seeded shuffle (seed 2025) partitions 1,000 participants into 800 training participants (19,200 windows) and 200 held-out test participants (4,800 windows), verified disjoint. Within the 800 training participants, 5-fold `GroupKFold` cross-validation (grouped by participant) provides a stability estimate. The held-out test set is touched exactly once, after final training on all 800 training participants, never during cross-validation or any hyperparameter selection. All error metrics use circular clock-time differences computed on decoded hours.

## 5. Independent State-Based Estimator and Fusion

A second, mechanistic `current_DLMO` estimate is produced by a state engine implementing the same three-layer transition model (§1), computed purely from behavioral history and state continuity, with no dependency on the trained XGBoost model. Because this state engine is the same implementation used by the synthetic data generator, the state estimator and the synthetic ground-truth trajectory share identical transition mathematics — a fact material to interpreting the fusion diagnostic (see `results_draft.md`, §4). A fusion layer combines the XGBoost estimate and the state estimate through a locked four-layer model: data-quality-tiered base weights, a disagreement-based weight adjustment, a biological-continuity cap on day-over-day change, and a confidence penalty by disagreement regime. Fusion combines weighted unit-circle vectors rather than averaging clock hours directly.

## 6. Alignment, Contribution, and Recommendation

An alignment engine converts the fused DLMO and a participant's actual behavior into a 0-100 score, `0.60 * phase_alignment + 0.40 * behavioral_alignment` (a locked project weighting, not a scientifically validated ratio). A contributor-ranking engine identifies which of five tracked behavioral signals most contributes to current misalignment, in strictly non-causal ("modeled influence") language. A deterministic recommendation engine (no LLM) converts ranked contributors into one primary intervention plus up to two supporting nudges, drawn from a fixed catalogue of six behavioral interventions, using a graduated-target rule that never asks for the theoretically ideal value immediately.

## 7. Effectiveness, Personalization, and Safety

An observational effectiveness system measures whether a recommended intervention is *associated with* improved alignment through a three-phase progression of increasingly rigorous non-causal analysis (before/after comparison → matched comparison → personal regression), gated by independent sufficiency thresholds at each phase. A personalization engine graduates each (participant, intervention-type) pair through `literature → personal_ranking → personal_effect → adaptive_policy`, governed at its most mature stage by a Thompson-sampling contextual bandit restricted to the approved catalogue. A safety layer sits above the completed pipeline, deciding only whether/how to display already-computed output — never recomputing a prediction — via confidence gating and four rolling-window unusual-pattern detectors, with a hard-coded language guard blocking any medical or diagnostic phrasing.

## 8. Application Layer

The system is exposed through a FastAPI backend (`/api/v1`, strictly layered: routes → services → repositories, no domain logic in routes) and a React/TypeScript dashboard that performs no domain computation of its own. Both are explicitly documented prototypes: no authentication, authorization, production rate limiting, or CORS/TLS configuration is implemented.

## 9. System-Wide Audit

Phase 17 conducted a system-wide adversarial audit (349 new backend tests, 18 new frontend tests) across every layer described above, finding and fixing six real defects and concluding a final status of **CONDITIONAL PASS**, with three specific limitations deliberately left unresolved and documented (see `limitations_draft.md`).
